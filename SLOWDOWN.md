# SLOWDOWN.md — `maxShadowFiles: 0` tsserver slowdown: findings

Status: analysis only. No code changed. This document is the input for a future fix task.

## TL;DR

`maxShadowFiles: 0` (documented as "0 disables threshold", README.md:227) also disables the only
size guard that keeps the plugin off expensive projects. In `shadow` (and partly `hybrid`) mode,
this forces large projects onto the shadow runtime, whose cache design collapses under normal
editing patterns: the shadow context cache is **single-slot and keyed by file name + project
version**, so every file switch or edit disposes the shadow language service and rebuilds a
**whole second TypeScript program synchronously, on the LS request path**. Measured cost:
**hundreds of ms per request** on a synthetic 1000-file project vs **2-6 ms** when the fallback
threshold is active — the "types take a second or longer to load" symptom.

## How `0` disables the guard

- `src/plugins/tsserver/index.cjs:53` — unset and explicit `0` normalize to the same value:
  `Number.isFinite(maxShadowFiles) && maxShadowFiles > 0 ? maxShadowFiles : 0`.
- `src/plugins/tsserver/index.cjs:67` — `canUseShadowRuntime` treats `maxShadowFiles <= 0` as
  "shadow runtime always allowed" and returns `true` without ever calling `getScriptFileNames()`.
- With a positive threshold and `autoFallbackToSuppress` (default true), a project bigger than
  the threshold silently falls back to cheap `suppress` mode (index.cjs:71-73). With `0`, that
  escape hatch is gone and large projects stay on the shadow path forever.

Note: because unset config also normalizes to `0`, any shadow/hybrid project that does not set
`maxShadowFiles` runs with **no size guard at all** — this is not exclusive to explicitly setting 0.

## The expensive path (what happens on every cache miss)

For every proxied feature request (`getSemanticDiagnostics`, `getQuickInfoAtPosition`,
`getCompletionsAtPosition`, `getCompletionEntryDetails`, inlay hints) in shadow mode:

1. `getShadowSemanticDiagnostics` (shadow-language-service.cjs:924) calls
   `createShadowContext` (758) **synchronously, on the request path**.
2. Cache key (780): `` `${getOptionsKey(options)}:${fileName || ""}:${getProjectVersion(...)}` ``
   — it includes the **file name**. The cache is a single slot per host (`shadowCacheByHost`,
   WeakMap, line 16). Consequences:
   - Open/switch to a different file → key mismatch → full rebuild, even when nothing changed.
   - In a real tsserver host, `getProjectVersion()` (line 25) bumps on **any** edit anywhere in
     the project → every version bump invalidates the slot → full rebuild.
3. On miss, the previous shadow LS is disposed (785-786) and rebuilt from scratch:
   - `rewriteProgramFiles` (651) — with `shadowScope: "project"`, walks **every file in the
     program** through `collectRewriteEdits` + `checker.isTypeAssignableTo` (the documented perf
     hotspot, AGENTS.md "Perf hotspot" row).
   - `createShadowLanguageService` (687) — builds a **fresh `ts.createLanguageService`** (738).
     Its shadow host lists **all project files** (690) even when `shadowScope: "file"` — so the
     first semantic request against it is a **full cold program build + check**, not a per-file one.
4. Only after that does the actual feature call run. The host program build is paid separately
   (index.cjs:85 `getProgram()`), so cold start on a large project ≈ **two full program builds**
   before first diagnostics.

Hybrid mode hides this only partially: `scheduleWarmup` (hybrid-coordinator.cjs:82-112) runs
`warmShadowContext` inside a `setTimeout`, so the same full rebuild still **blocks the event loop**
when it fires; plus `canServeFromShadow` (115) needs an exact `readyKey` match that includes file
name and version, so it thrashes the same way.

Additionally, every `getSemanticDiagnostics` request runs
`getOperatorAnnotationDiagnosticsForFile` (index.cjs:86, annotation-diagnostics.cjs:213) — a
full AST walk of the file with the checker. Minor next to the rebuild, but it is on the same path.

## Measured evidence

Synthetic project generated by the harness described below; warm host LS, `mode: "shadow"`.
Numbers are `getSemanticDiagnostics` wall time per request (Node 22, TS 5.9.3, this machine):

| Scenario | maxShadowFiles 0 / unset | threshold active (fallback) |
|---|---|---|
| 300 files, scope=project, first (cold) request | 826 ms | 527 ms |
| 300 files, scope=project, per file switch | 214-266 ms | 2-6 ms |
| 300 files, after single-file edit (version bump) | 303 ms | 18 ms |
| 1000 files, scope=file (default), per file switch | 354-437 ms | 2-6 ms |

~70-100x per-request penalty, matching "a second or longer" once real-world file sizes,
`node_modules` type graphs and lib files are involved.

Repro harness sketch (also how `scripts/run-tests.cjs` builds its in-process LS):

```
host with getScriptFileNames/getScriptVersion/getProjectVersion bumping on edit
ts.createLanguageService(host, ts.createDocumentRegistry())
createPlugin({typescript: ts}).create({languageService, languageServiceHost: host,
    config: {mode: "shadow", maxShadowFiles: 0, shadowScope: "project"}, project: {}})
→ time pluginLS.getSemanticDiagnostics() while alternating file names / bumping versions
```

## Contributing factors (ranked)

1. **Single-slot cache keyed with fileName** (shadow-language-service.cjs:780) — file switches,
   which editors do constantly, guarantee misses. The slot also stores project-wide state, so
   serving file B never reuses the context built for file A.
2. **Dispose + full rebuild on every miss** (785-786, 738) — no incremental path. The reused
   `documentRegistry` (775, 795) softens re-parsing, but program graph/checker work is redone
   from zero every time.
3. **`<= 0` bypasses the size guard entirely** (index.cjs:67) — the exact mechanism meant to
   protect large projects is off exactly where it is needed.
4. **`shadowScope: "project"` re-rewrites all files per rebuild** (655-657) via the
   `isTypeAssignableTo`-heavy resolver; scope `"file"` only trims step 2's rewrite walk, the
   shadow program is still whole-project (690).
5. **Synchronous execution on the feature-request path** — editors request diagnostics on open
   and on every edit; each request pays the full rebuild inline.
6. `canUseShadowRuntime`/`getPluginOptions` run per request and rebuild the file-name array each
   time — negligible, but on the hot path.

## Suggested fix directions (for the follow-up task)

- **Do not dispose the whole shadow program on file switch.** For `shadowScope: "project"` the
  context is whole-program: serve any file from it, and key the cache by
  `optionsKey:projectVersion` only (drop fileName from the key). For `shadowScope: "file"`, keep
  a small LRU/Map of per-file contexts instead of one slot.
- **Reuse the shadow LS across version bumps** instead of recreating it: the shadow host already
  delegates `getScriptVersion` to the base host (691), so keeping the LS alive and letting the
  document registry do incremental updates turns rebuilds into re-checks.
- **Keep a size heuristic even when `maxShadowFiles` is 0** (or introduce a distinct value for
  "no fallback"), and/or warn once when the shadow path is entered on a big project.
- Consider debouncing/async shadow rebuilds in `shadow` mode the way `hybrid` does, while
  continuing to serve from the host LS in the meantime (preserve the never-crash-the-LS
  invariant and the suppress fallback).
